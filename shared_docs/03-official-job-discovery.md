# 03 企业官方岗位发现模块开发手册

## 1. 模块目标

输入一个目标 JD 和用户求职约束，发现仍有申请入口且与目标相似的岗位，只返回企业官方招聘渠道。模块不登录用户账号、不自动填写、不自动投递。

输出不应只有 URL，还应包括：

- 企业和岗位标准名称；
- 工作地点、岗位类型和面向毕业年份；
- 官方来源与页面快照；
- 开放状态、最后核验时间和置信度；
- 与目标 JD 的相似点；
- 用户满足/不满足的硬门槛；
- 关键能力差距；
- 用户手动打开官网的入口。

## 2. 处理流水线

```text
目标 JD 解析
  → 生成岗位画像
  → 生成多组搜索查询
  → 搜索服务获取候选 URL
  → 官方域名和路径识别
  → 页面抓取/渲染
  → 正文与结构化字段提取
  → 岗位实体去重
  → 开放状态核验
  → 硬门槛判断
  → 能力匹配与排序
  → 返回带证据的候选岗位
```

## 3. 输入定义

### 3.1 从目标 JD 提取

- 岗位族与职级；
- 技术栈和业务方向；
- 学历、专业、毕业年份；
- 实习/校招/社招；
- 工作地点和到岗要求；
- 明示和隐含能力；
- 关键词、同义词和排除词。

### 3.2 用户补充约束

- 目标城市及是否接受远程；
- 可实习周期、每周天数、最早到岗日期；
- 毕业年份、学历和专业；
- 行业偏好与排除企业；
- 不接受的要求，如出差、转正不确定等；
- 搜索范围：完全相似/可迁移/冲刺。

## 4. 官方来源识别

### 4.1 来源等级

| 等级 | 来源 | 默认处理 |
|---|---|---|
| A | 企业自有官方招聘域名 | 可直接进入候选 |
| B | 企业官网内的招聘页面 | 可直接进入候选 |
| C | 企业官方使用的第三方 ATS 域名 | 需建立企业—ATS 绑定证据 |
| D | 学校就业网转载 | 仅作为发现线索，不作为最终申请入口 |
| E | 招聘平台、自媒体、聚合站 | 仅作为线索或排除 |

第三方 ATS 页面不能仅因域名常见就认定为官方，必须确认页面上的企业身份、官网跳转关系或企业官方招聘页的外链。

### 4.2 官方域名表

为首批 20～30 家企业维护配置：

```yaml
company: 示例科技
official_domains:
  - careers.example.com
ats_domains:
  - example.jobs.vendor.com
job_path_patterns:
  - /jobs/
  - /campus/position/
blocked_paths:
  - /news/
  - /privacy/
```

配置必须版本化并提供后台修正入口，不能把规则散落在采集代码中。

## 5. 页面抓取策略

按成本分级处理：

1. 普通 HTTP 获取静态 HTML；
2. 如果正文缺失，再使用无头浏览器渲染；
3. 若页面调用公开岗位接口，在遵守网站规则前提下使用接口；
4. 遇到登录、验证码、明确禁止自动访问或高风险反爬时停止，不绕过；
5. 失败时保留原因并允许用户手动打开官网。

抓取时保存：URL、状态码、抓取时间、正文哈希、标题、结构化数据和必要网页快照。原始页面不无限期保存，具体见合规手册。

### 5.1 首版实现边界

首版采用“企业白名单 + 站点适配器 + 统一输出 Schema”，不以通用爬虫覆盖所有招聘网站。每个生产适配器必须登记：

- 允许访问的官方域名和路径模式；
- 选择器/接口版本及最后审核时间；
- 静态页面测试夹具和预期字段；
- 限流、超时、缓存和失败降级策略。

默认先用普通 HTTP 静态解析；只有静态正文缺失且站点规则允许时，才启用 Playwright 作为二级动态解析方案。Scrapy 可在后续有明确规模和性能证据时评估，但不是 CP-005 前置依赖；`newspaper3k` 不纳入招聘页面核心解析。

采集失败必须返回结构化失败原因和人工打开入口，禁止用模型补全缺失事实。新域名加入生产白名单前，必须审核站点条款、robots、域名归属和实际字段需求。

适配器最小接口：

```text
discover(query, limits) -> candidate_urls
fetch(url, policy) -> raw_page
extract(raw_page, parser_version) -> JobExtraction
verify(raw_page, extraction) -> OpenStatusSignals
```

适配器不得返回最终推荐分、最终开放状态或执行申请动作；这些结论由后端规则和核验流程统一产生。

## 6. 岗位结构化提取

优先级：页面结构化数据 > 可配置选择器 > 通用规则 > 大模型候选提取。

至少提取：

- `job_title`
- `company`
- `locations`
- `employment_type`
- `recruitment_type`
- `graduation_years`
- `education`
- `major_constraints`
- `responsibilities`
- `requirements`
- `preferred_requirements`
- `published_at`
- `deadline`
- `apply_url`
- `source_quotes`

所有字段必须允许 `UNKNOWN`，禁止模型用常识补全网页没有的信息。

## 7. 开放状态核验

状态枚举：

- `OPEN_CONFIRMED`：申请按钮可用，未发现截止或下线提示；
- `OPEN_PROBABLE`：页面有效但无法完整验证申请流程；
- `UNKNOWN`：信息不足或页面访问失败；
- `CLOSED`：明确截止、下线或按钮不可用；
- `REMOVED`：页面不存在或职位不存在；

核验信号包括：

- HTTP 和页面渲染是否成功；
- 是否出现“立即申请/投递简历”等操作；
- 按钮是否禁用；
- 是否存在明确截止时间；
- 页面是否提示职位已下线；
- 申请链接是否仍指向对应职位；
- 页面是否为通用人才库而非具体岗位；
- 最后核验距离当前时间多久。

前端默认只展示 `OPEN_CONFIRMED` 和 `OPEN_PROBABLE`，并分别标注“已核验”和“建议打开确认”。不得承诺“保证可投”。

## 8. 去重与实体对齐

同一岗位可能拥有不同地区页面、语言页面、追踪参数或校招批次。去重使用：

1. 规范化 URL，删除追踪参数；
2. 优先使用页面岗位 ID；
3. 标准化企业、标题、地点和发布时间；
4. 计算职责和要求文本相似度；
5. 保留来源更官方、更新时间更新、申请入口更明确的记录；
6. 不能确定时建立“可能重复”关系，不强行合并。

## 9. 匹配与排序

先执行硬门槛，再计算软匹配。

```text
候选最终分 =
  能力匹配 35%
  岗位语义相似 20%
  用户偏好 15%
  官方与开放可信度 20%
  信息完整度 10%
```

存在明确硬门槛不满足时，不进入“推荐投递”，但可以出现在“为什么不适合”区域。未知条件不能视为满足，应显示待确认。

结果分组优于一个模糊总分：

- 现在适合投；
- 完成一项关键补齐后再投；
- 冲刺岗位；
- 硬门槛不符；
- 状态待确认。

## 10. MVP 与验收

### MVP

- 支持 20～30 家企业；
- 每家至少一条稳定发现路径；
- 目标 JD 自动生成搜索查询；
- 静态和动态页面两级抓取；
- 结构化解析、官方域名判断、去重和开放状态；
- 用户可以查看每项判断的原文；
- 不登录、不投递。

### 验收指标

- 官方来源准确率：100%；
- 岗位字段抽取 F1：核心字段不低于 0.85；
- 硬门槛判断准确率：不低于 90%；
- 去重准确率：不低于 90%；
- 开放/关闭状态准确率：不低于 85%；
- Top-5 结果人工相关性：平均不低于 4/5；
- 单次发现任务 95% 在 90 秒内返回首批结果。

## 11. 降级策略

- 动态站点难以稳定采集：缩小企业范围，优先稳定官网；
- 搜索服务受限：使用企业配置表和站内搜索入口；
- 开放状态无法确定：标记 `UNKNOWN`，不混入已核验结果；
- 大模型提取不稳定：增加 JSON Schema、规则兜底和人工标注测试集；
- 页面结构频繁变化：以配置化解析器替代逐站硬编码发布。
