# 15 云码道可领取任务 Backlog

## 1. 使用方式

云码道按依赖关系领取任务，不按文件顺序随意开发。每个任务的完成结果必须写回 CodeArts 工作项，并符合 `00-codeartsdoer-master.md` 的 DoD。

优先级：`P0` 必须完成，`P1` 时间允许完成，`P2` 初赛不做。

状态建议：`TODO → IN_PROGRESS → REVIEW → ACCEPTED`，阻塞使用 `BLOCKED` 并附证据。

当前状态以 [18-current-state-and-next-actions.md](./18-current-state-and-next-actions.md) 为准。当前 `CP-001` 为 `PARTIAL`：Git 仓库、`main` 分支、GitHub 远端和首个文档提交已完成；CodeArts 项目/流水线、应用骨架、健康检查和启动脚本仍待完成。云码道不得重复执行已完成的 Git 初始化，也不得将 `PARTIAL` 当成 `ACCEPTED`。

## 3. 任务卡

### CP-001：新仓库、环境与 CodeArts 初始化（P0）

依赖：无。负责人：成员 C/D。

交付：新 Git 仓库、分支策略、README、许可证、`.env.example`、本地启动骨架、健康检查、CodeArts 项目/工作项/流水线骨架。

验收：干净环境可启动 API 和前端；秘密扫描通过；提交与工作项关联；不含 MindSpace 文件或历史。

### CP-002：数据库迁移与跨模块契约（P0）

依赖：CP-001。负责人：成员 C，协作者 A/D。

交付：RDS 表设计、迁移脚本、`/api/v1` OpenAPI、JSON Schema、错误码、种子数据和契约测试。

验收：可重复初始化；外键和唯一约束有效；示例能被前端和 Worker 共同解析；未知字段、版本和时间规则通过测试。

### CP-003：JD/简历解析与事实确认（P0）

依赖：CP-002。负责人：成员 B，协作者 A/D。

交付：文本/PDF/DOCX 导入；结构化提取；原文定位；技能归一化；用户确认和修正；解析失败与重试。

验收：固定样例核心字段 F1≥0.85；无来源字段为 `UNKNOWN`；每条技能可定位原文；失败不阻塞其他目标。

### CP-004：能力标准、证据聚合与差距引擎（P0）

依赖：CP-002、CP-003。负责人：成员 C/A。

交付：15～25项 Java 后端能力、L0～L5 锚点、证据权重/上限、冲突处理、差距分类、优先级、岗位匹配计算和历史快照。

边界：首版使用 PostgreSQL/RDS 关系表实现逻辑图谱；ESCO/O*NET 只作字段参考，Open Skills 等外部数据须完成来源与许可证审查后才能使用；不引入图数据库。

验收：相同输入可重复；低可信证据有上限；证据不可重复计权；硬门槛和未知状态正确；结论可追溯。

### CP-005：企业官方岗位发现与核验（P0）

依赖：CP-002、CP-003。负责人：成员 B。

交付：15～30家企业配置；查询生成；静态/动态抓取；官方来源判定；字段提取；去重；开放状态；限流、失败和快照。

边界：采用企业白名单、站点适配器和统一 Schema；静态 HTTP 优先，Playwright 仅作二级方案；Scrapy 不是前置依赖；不使用 `newspaper3k` 作为核心招聘解析器，不登录、不绕过限制、不自动投递。

验收：官方来源准确率100%；开放状态准确率≥0.85；不得登录/绕过限制；每条结果有 URL、核验时间和状态理由。

### CP-006：分层题库与自适应测试（P0）

依赖：CP-004。负责人：成员 A/C。

交付：至少100道首版题；题型和量表；规则选题状态机；客观评分；开放题 Schema；复测等价题；证据写回。

验收：题目按证据不足和不确定性选择；难度可升降；至少两种题型；10分钟内完成一次测评；客观分不依赖模型。

### CP-007：靶向文本面试（P0）

依赖：CP-004、CP-006。负责人：成员 B/A。

交付：面试蓝图；项目深挖、岗位知识和场景模式；动态追问；评分引用；会话恢复；报告。

边界：使用自定义状态机 + MaaS；不引入 Rasa/Botpress；状态、题量、追问和评分写回由程序控制，模型仅提供分析和表达候选。

验收：80%问题可映射 JD/简历；追问与回答相关；评分不夸大；中断可恢复；结论写回图谱。

### CP-008：学习任务、实践和复测闭环（P0）

依赖：CP-004、CP-006、CP-007。负责人：成员 C/A。

交付：资源库、链接核验、任务模板、能力依赖、时间排程、状态机、实践提交、验收、复测和计划调整。

验收：正式任务均对应差距；≥80%有产物和验收；不超时间预算；前置顺序正确；复测结果能改变后续计划。

### CP-009：证据化简历建议（P1）

依赖：CP-003、CP-004、CP-008。负责人：成员 D/A。

交付：简历版本、JD 对齐、逐条建议、证据引用、用户确认、ATS 单模板和差异对比。

验收：无依据新增事实数为0；用户确认前不覆盖原文；实践成果能生成候选句；版本互不覆盖。

### CP-010：前端端到端工作台（P0）

依赖：CP-003、CP-004、CP-005、CP-006。负责人：成员 D。

交付：目标创建、导入、能力矩阵、测评、面试、岗位、学习、简历页面；来源抽屉；加载/空/失败/重试状态。

验收：非开发者15分钟内完成首次分析；主要按钮均有真实 API；不以 Mock 结果作为最终演示；移动端至少可读。

### CP-011：云部署、监控与评测（P0）

依赖：CP-006～CP-010。负责人：成员 D/C/A。

交付：OBS/RDS/Redis/MaaS/ECS 或云容器接入；流水线；日志、告警、配额；离线评测集；用户实验和消融结果。

边界：初赛以 Docker Compose 本地复现、ECS 或云容器部署为准；Kubernetes 不是前置条件；Python Worker 不替代 Spring Boot 主 API。

验收：可从零部署；关键指标有原始数据；外部失败可降级；演示账号脱敏；流水线失败不覆盖稳定环境。

### CP-012：冻结、提交与答辩（P0）

依赖：CP-011。负责人：全员，A统筹。

交付：提交仓库、README、数据、许可证、演示视频、PPT、评测报告、CodeArts 留痕和问答库。

验收：文档、代码和演示一致；每位成员能解释核心贡献；线上和离线演示均成功；所有限制和失败案例已披露。

## 4. 并行规则

CP-003 与 CP-004 的标准库可在契约冻结后并行；CP-005 可与二者并行但必须使用 CP-002 的岗位 Schema；CP-006 题库编写可先行，接入状态机必须等 CP-004；CP-009 不得早于 CP-008 生成实践证据；CP-010 只能在契约固定后开始真实联调。
