- 测评状态机与证据写回；

### 成员 D：前端、云部署与集成负责人

- Vue 3 交互页面；
- 能力矩阵、测评、面试和课程表；

- 端到端集成测试。

所有核心模块至少有第二责任人，避免单点失联。

## 6. P0 功能完成定义

一个功能只有同时满足以下条件才算完成：

- 有明确用户入口和成功/失败状态；
- 接口、数据和错误路径实现；
- 至少有自动测试或可复现验收脚本；
- 关键结果带来源和日志；
- 已部署到集成环境；
- 由非开发者本人完成一次验收；
- 更新相应文档和 CodeArts 任务状态。

## 7. 降级顺序

若进度滞后，按以下顺序删除或简化：

1. 取消语音、实时对话和复杂动画；
2. 取消自由拖拽课程表和 ICS 导出；
3. 简历只保留建议和单模板，不做复杂编辑器；
4. 企业从30家缩至15家高质量稳定站点；
5. 能力项从25项缩至15项核心技能；
6. 微型实践缩至3个高质量任务。

不能删除：证据图谱、自适应测评、官方岗位核验、差距到学习再到复测的闭环。

## 10. 外部参考作品对比与吸收计划

### 10.1 参考对象与结论边界

参考作品：[《黑马用大模型把招聘搜索彻底重做了一遍！》](https://mp.weixin.qq.com/s?__biz=MzI0NjM3NjI1NQ==&mid=2247622605&idx=1&sn=9c1ddbb7fb555432f5db27c10d4dd170)，黑马程序员公众号，2026-09-15。文中项目名为“黑马直聘”。

该作品与本项目都把大模型用于招聘文本的结构化理解，而不是只做聊天或文案生成；它重点解决“职位文本与搜索词字面不一致导致漏召回、引流词导致误召回”，本项目重点解决“学生面对目标岗位时不知道真实差距、证据是否可靠以及如何补齐”。因此，两者在 **JD 结构化和语义检索上直接相关**，但核心用户、数据来源、产品闭环和参赛创新点不同。

文章属于项目介绍和课程宣传材料，公开页面未提供可复现代码、标注集或检索指标。计划中只吸收可解释的工程方法，不把文中的“又准又全”等表述当作已验证基准，也不复制其代码、提示词、数据或目录结构。

### 10.2 联系与区别

| 维度 | “黑马直聘” | “职径” | 对本项目的含义 |
|---|---|---|---|
| 招聘场景 | 招聘方发布职位、求职者检索职位 | 学生导入目标 JD 和简历，发现岗位并准备求职 | 上游文本理解相通，下游用户任务不同 |
| 核心问题 | 提高职位搜索的召回准确性，减少字面漏召和引流词误召 | 解释硬门槛与能力差距，用证据、测评、学习和复测形成成长闭环 | 不能把项目收缩成普通招聘搜索系统 |
| 数据入口 | 平台内新发布职位，可在发布时立即抽取 | 外部企业官方招聘页、用户提供的 JD/简历和约束 | 本项目无法控制发布端，抽取发生在导入或采集后 |
| 结构化方法 | 基础抽取后，按用工、场所、结算、时间、福利等字段并行归一化 | 提取岗位、硬门槛、技能、证据、开放状态并映射统一能力标准 | 可借鉴“基础事实与字段归一化分离”的分阶段设计 |
| 检索方法 | 缓存判断关键词所属字段，再在 Elasticsearch 中按字段检索 | 企业白名单发现、站点适配器抓取、官方性与开放状态核验、硬门槛和能力排序 | 可借鉴字段化检索，但必须保留官方来源与状态核验 |
| 大模型边界 | 负责职位理解和标签抽取，检索仍由搜索引擎执行 | 负责候选提取、追问和解释；硬门槛、计分、状态流转由程序控制 | “模型理解、程序决策”原则一致 |
| 异步与观测 | Kafka 解耦发布/消费/搜索，Langfuse 与 LiteLLM 双层 Trace | Spring Boot 编排异步任务，Python Worker 执行采集/AI，统一审计和日志 | 可借鉴全链路关联 ID，不必照搬中间件组合 |
| 图谱含义 | 主要围绕职位标签和关键词—字段映射 | 岗位—能力—证据—题目—学习任务之间的可追溯关系 | 本项目图谱范围更广，是主要差异化基础 |
| 最终输出 | 可检索的职位列表 | 官方岗位、差距解释、能力校准、学习任务、复测和简历建议 | 本项目竞争力在搜索之后的证据化闭环 |
| 评测责任 | 文章强调架构与技术亮点，未披露完整离线指标 | 预先规定字段 F1、Precision@5、硬门槛、开放状态、用户实验和消融 | 必须用数据证明提升，不能只展示技术名词 |
| 合规边界 | 主要处理平台内发布数据 | 访问外部官方站点并处理个人简历 | 需额外处理 robots/条款、限流、授权、脱敏和删除 |

### 10.3 可借鉴设计及本项目化改造

#### P0：纳入首版

1. **统一岗位语义字典**：在 CP-002/CP-003 冻结岗位族、技能、城市、招聘类型、学历、毕业年份、到岗要求、工作方式等标准字段，同时维护别名、否定表达和排除词。原文没有的信息保持 `UNKNOWN`。
2. **分阶段结构化流水线**：先从页面结构化数据、选择器和正文中抽取基础事实，再分别执行字段归一化、Schema 校验和来源绑定，最后才进入硬门槛与匹配规则。每个结果保留 `source_quote`、解析版本和置信度。
3. **两阶段发现与排序**：第一阶段通过企业白名单和多组查询召回官方候选；第二阶段按标准字段、硬门槛、开放可信度和能力差距排序。正文中的导航、推荐职位、宣传语和否定语句不得直接成为岗位标签。
4. **端到端关联追踪**：为一次分析统一传递 `traceId + taskId + goalId`，记录“发现、抓取、抽取、归一化、核验、匹配、写回”各阶段耗时、输入输出哈希、模型版本、重试和失败原因。
5. **基线与消融**：保留纯关键词/全文匹配基线，与“标准字段 + 硬门槛”和完整“证据图谱 + 开放核验”方案对比，报告 Precision@5、字段 F1、误召回、漏召回、延迟和模型成本。

#### P1：有余量再做

1. 用标准技能与岗位别名字典提供搜索输入联想，但联想只帮助输入，不直接决定匹配结果。
2. 对互不依赖的字段归一化并发执行；只有在性能测试证明收益、且限流与费用可控后启用。
3. 为解析与匹配提供阶段级观测视图，演示时展示一条结果如何从原文变成标准字段和最终解释。

#### 暂不照搬

- **不因参考作品使用 Kafka 就新增 Kafka**：首版沿用既定异步任务方案；只有出现可复现的任务丢失、积压、吞吐或独立扩容问题，并完成运维成本评估后再立项。
- **不因参考作品使用 Elasticsearch + IK 就新增搜索集群**：首版数据规模仅 300～500 条评测岗位，优先使用 PostgreSQL/RDS 的结构化查询与现有搜索服务；只有基准测试证明查询质量或性能达不到验收线后再评估。
- **不为展示工作流而直接引入 LangGraph**：先用可测试的 Python 流水线和显式状态实现；当分支、恢复、并行和状态传播已明显难以维护时再评审编排框架。
- **不把 Langfuse + LiteLLM“双 Trace”当目标**：首版目标是一次业务任务可端到端关联、日志脱敏且能定位失败；观测工具服从这一目标。
- **不提前微调模型**：先完成通用模型、规则和 Schema 的基线。只有固定评测集证明错误稳定集中、具备合法标注数据且预算允许时，才评估 SFT/LoRA；DPO 不进入初赛前置范围。

### 10.5 答辩表述

建议表述为：

> “黑马直聘”证明了大模型可以把自然语言职位转成可检索的标准字段。职径吸收这一上游方法，但不止解决‘搜得到’，还核验岗位是否官方、是否仍开放，并继续回答‘我是否满足、证据是否可靠、怎样补齐、补齐后是否真的提升’。我们的创新重点是岗位—能力—证据—行动的可验证闭环。
