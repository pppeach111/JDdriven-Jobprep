# 01 产品定义与范围手册

## 1. 产品定位

职径面向高校实习和校招用户，以目标 JD 为入口，帮助用户完成：

1. 找到仍可申请的企业官方相似岗位；
2. 判断岗位硬门槛和个人能力差距；
3. 通过低成本测评与靶向面试校准能力；
4. 将差距转换为可执行、可验收的学习计划；
5. 将真实成果转化为有证据支撑的简历内容；
6. 由用户跳转官网并手动完成申请。

一句话价值主张：

> 不只告诉用户“你与岗位匹配多少”，还说明差在哪里、证据是什么、怎样补齐，以及补齐后能否被重新验证。

## 2. 目标用户

### 2.1 首要用户

- 大二至研二，准备实习或秋招；
- 已有一份基础简历，但不清楚与目标岗位的真实差距；
- 能提供一个或多个目标 JD；
- 每周可投入 5～15 小时学习；
- 缺少系统求职辅导或付费咨询预算。

### 2.2 暂不服务

- 社招高级管理或十年以上经验岗位；
- 需要执业资格认证的医疗、法律等岗位；
- 希望批量自动投递、自动聊天或绕过招聘平台限制的用户；
- 需要正式职业能力认证结果的机构。

## 3. 核心用户故事

### 故事 A：从一个 JD 找相似官方岗位

用户上传或粘贴 Java 后端实习 JD，填写城市、毕业年份、到岗时间等约束。系统解析岗位能力，搜索企业官方招聘页，只显示经过开放状态核验的候选岗位，并解释相似原因与硬性门槛。

### 故事 B：验证自己是不是真的会

系统发现用户简历声称“熟悉 Redis”，但缺少可靠证据，于是发起 8～10 分钟自适应测试。测试经过概念、代码阅读、故障诊断和场景追问后，将 Redis 能力估计为 L2.6，置信度 72%。

### 故事 C：把差距转成行动

系统判断“Java 并发”和“性能测试”是目标岗位最重要且可短期补齐的差距，生成两周计划。每个任务包含官方资料、开源示例、实践产物、验收条件和复测。

### 故事 D：让简历内容跟成长同步

用户完成缓存改造与压测任务，提交代码和结果。系统将已验证成果转化为简历建议，但要求用户确认事实，不允许自动添加未发生的经历。

## 4. 核心闭环

首版必须完整跑通以下状态，而不是只完成若干独立页面：

```text
创建求职目标
  → 解析 JD、简历和用户约束
  → 生成初始岗位能力图谱
  → 核验硬门槛
  → 选择证据不足的关键能力
  → 完成自适应测试/文本面试
  → 更新能力估计与置信度
  → 生成差距优先级
  → 生成学习和实践任务
  → 复测并提交实践证据
  → 更新岗位匹配度
  → 生成简历改写建议
  → 跳转官方岗位手动申请
```

## 5. MVP 范围

### 5.1 P0：缺少即无法参赛演示

- JD 文本/文件导入与结构化解析；
- PDF/DOCX 简历导入与基础解析；
- 用户求职硬约束填写；
- Java 后端能力标准库；
- 能力—证据—差距图谱；
- 20～30 家目标企业官方岗位搜索；
- 岗位去重、硬门槛判断、开放状态核验；
- 10分钟文本自适应测评；
- 面向简历项目的动态追问；
- 差距驱动的两周学习计划；
- 复测后更新能力和岗位匹配度；
- 两套 ATS 友好简历模板或简历建议视图；
- 可解释结果和原文定位；
- 华为云部署与完整演示账号。

### 5.2 P1：时间允许再完成

- Git 仓库项目证据读取；
- 课程表拖拽、ICS 日历导出；
- 多个目标 JD 的共同能力分析；
- 岗位变更订阅与提醒；
- 简历 PDF 导出和多版本对比；
- 面试报告分享。

### 5.3 P2：明确延后

- 自动投递、自动登录或自动填写网申；
- 实时语音或视频面试；
- 覆盖所有岗位类别；
- 在线 IDE 和大型 OJ；
- 大量花哨简历模板；
- 招聘平台账号数据抓取；
- 正式人才认证或心理测评。

## 6. 成功标准

产品演示成功不等于“每个按钮都能点”。首版验收必须同时满足：

- 对测试集中的岗位，硬门槛判断准确率不低于 90%；
- 返回结果全部具有企业官方来源，失效岗位比例可测且明确展示；
- 每个匹配或不匹配结论可以追溯到 JD、简历、测试或实践证据；
- 同一用户完成测评前后，能力等级和置信度产生可解释变化；
- 学习计划至少 80% 的任务包含资源、产物、验收标准和复测；
- 简历建议不产生用户未提供、未确认的事实；
- 真实用户可在 15 分钟内完成 JD 导入、初始分析和一次快速测评。

## 7. 非目标与防跑偏检查

每次需求评审都询问：

1. 这个功能是否直接增强“岗位—能力—证据—行动”闭环？
2. 没有它能否完成核心演示？
3. 是否已经存在成熟工具，而我们只是重复实现？
4. 是否会引入账号、反爬、隐私或部署风险？
5. 是否能在两周内得到可测量结果？

如果第1项为否，或第2项为是且开发成本较高，默认移入 P2。

## 8. 关键产品用语

建议使用：

- “能力估计”而不是“能力认证”；
- “开放状态已核验/待复核”而不是“保证可投”；
- “官方岗位发现”而不是“全网爬虫”；
- “证据驱动匹配”而不是“AI算命式匹配”；
- “简历建议”而不是“自动编造简历”；
- “自适应测评”而不是“考试”；
