# 04 岗位—能力—证据图谱开发手册

## 1. 定义

能力图谱是系统对以下问题的可计算表达：

- 目标岗位需要哪些能力和硬门槛？
- 用户当前可能具备哪些能力？
- 每个判断由哪些证据支持或削弱？
- 差距属于资格、知识、实践、证据还是表达问题？
- 哪些行动能有效减少差距？
- 新测试、面试和实践完成后，结论如何更新？

它不是装饰性的节点关系图，也不是单一雷达分数。

## 2. 图谱核心节点

| 节点 | 示例 |
|---|---|
| JobGoal | 2027届 Java 后端实习 |
| JobPosting | 某企业后端开发实习生 |
| Requirement | 本科及以上、连续实习3个月 |
| Skill | Redis 缓存设计 |
| SkillDimension | 概念、代码、诊断、设计、表达、实践 |
| UserSkillEstimate | Redis L2.7 / 置信度74% |
| Evidence | 简历句子、测试回答、代码、压测报告 |
| Question | 缓存击穿诊断题 |
| LearningTask | 热点缓存改造实验 |
| ResumeClaim | “使用 Redis 优化查询性能” |

## 3. 图谱核心关系

```text
岗位 ─要求→ 能力
岗位 ─限制→ 硬门槛
能力 ─依赖→ 前置能力
用户 ─拥有估计→ 能力
证据 ─支持/削弱→ 能力估计
简历陈述 ─声称→ 能力
题目 ─测量→ 能力维度
回答 ─产生→ 测评证据
学习任务 ─提升→ 能力
实践产物 ─证明→ 能力
简历建议 ─引用→ 已确认事实/证据
```

## 4. 技能标准库

首版只建设 Java 后端岗位族，建议 20～25 项标准能力：

- Java 语法与集合；
- 面向对象与设计原则；
- 异常、泛型、反射；
- JVM 基础；
- Java 并发；
- Spring/Spring Boot；
- REST API 设计；
- MySQL 基础与索引；
- 事务与隔离；
- Redis 数据结构；
- Redis 缓存设计；
- 消息队列基础；
- Linux 与 Shell 基础；
- Git 协作；
- 单元测试；
- 日志与故障定位；
- 性能测试；
- 网络与 HTTP；
- 数据结构与算法；
- 系统设计基础；
- 项目表达；
- 需求理解与协作。

每项技能必须定义：

- 标准名称和别名；
- 边界和不包含的内容；
- L0～L5 行为锚点；
- 前置技能；
- 可使用的题型；
- 可接受证据类型；
- 适合的实践任务；
- 证据有效期建议。

## 5. 证据模型

### 5.1 证据类型与基础权重

| 类型 | 建议基础权重 | 说明 |
|---|---:|---|
| 用户自述 | 0.15 | 仅用于决定测什么 |
| 简历陈述 | 0.25 | 有表达但未验证 |
| 课程/证书 | 0.30 | 证明学习过，不等于会应用 |
| 项目描述 | 0.40 | 需验证真实性和个人贡献 |
| 客观题 | 0.45 | 适合知识，不足以证明实践 |
| 场景题 | 0.60 | 能体现应用和权衡 |
| 动态面试 | 0.65 | 能检验理解和表达 |
| 代码/仓库 | 0.75 | 需确认归属和关键贡献 |
| 微型实践 | 0.85 | 可自动验收且与能力直接相关 |
| 真实项目结果 | 0.90 | 有代码、数据、说明和可复现结果 |

基础权重不是最终置信度。还需乘以新鲜度、相关度、完整度和一致性。

### 5.2 证据事件不可覆盖

每次测试或任务都新增 Evidence，不覆盖旧记录。`UserSkillEstimate` 是对证据事件重新聚合后的当前快照。

必须保留：

- 来源与时间；
- 关联技能和维度；
- 支持或削弱方向；
- 原始内容或摘要；
- 评分规则版本；
- 模型/程序判断；
- 用户确认或申诉状态。

## 6. 能力估计

### 6.1 首版可实现公式

将每条证据映射为等级估计 `level_i` 和可靠度 `weight_i`：

```text
effective_weight_i =
  base_weight
  × relevance
  × freshness
  × consistency

estimated_level =
  Σ(level_i × effective_weight_i)
  / Σ(effective_weight_i)
```

置信度由有效证据总量、题型多样性和冲突程度计算，并设置上限：

- 只有自述和简历：最高 0.45；
- 有客观题但无应用题：最高 0.65；
- 有场景/面试证据：最高 0.80；
- 有可验收实践：可达到 0.90 以上。

这能阻止用户仅靠选择题被评为“精通”。

### 6.2 证据冲突

例如简历声称“熟练 Redis”，但场景题和追问表现为 L1：

- 不直接删除简历证据；
- 降低一致性系数；
- 标记“自述与测评不一致”；
- 触发另一种题型或实践任务；
- 在简历模块提示需要修改表述或补充证据。

## 7. 岗位要求建模

岗位要求不能只记录技能关键词。每条要求包含：

- `requirement_type`：硬门槛/核心/优先/加分；
- `required_level`：L0～L5；
- `importance`：0～1；
- `source_quote`：JD 原文；
- `extraction_confidence`：提取置信度；
- `is_explicit`：明示或推断；
- `human_confirmed`：是否人工确认。

推断出的隐含能力不得当作硬门槛，只能作为低权重参考。

## 8. 差距分类

| 差距类型 | 判断 | 系统行动 |
|---|---|---|
| 资格阻断 | 学历、年份、地点等不符 | 解释原因，不生成学习计划 |
| 知识缺口 | 基础概念或原理不足 | 学习单元 + 快速复测 |
| 应用缺口 | 会概念但不会解决场景 | 场景练习 + 代码阅读 |
| 实践缺口 | 没有真实实现和产物 | 微型项目/改造任务 |
| 证据缺口 | 声称会但缺少可靠证据 | 测试、面试或仓库验证 |
| 表达缺口 | 实践存在但讲不清楚 | 项目追问和结构化表达训练 |
| 可信度冲突 | 多条证据互相矛盾 | 换题型复测或人工确认 |

## 9. 差距优先级

```text
priority =
  岗位重要性
  × 等级差距
  × 同类岗位出现频率
  × 短期可提升系数
  × 证据不足系数
  × 目标紧迫度
```

约束：

- 资格阻断不参与学习优先级；
- 前置能力未满足时，后继能力暂不排到最前；
- 等级差距过大且剩余时间太短时，标记为冲刺而非承诺补齐；
- 多个岗位共同要求的能力提高优先级；
- 用户明确不愿学习的方向需给出影响，但不强制排程。

## 10. 岗位匹配展示

不建议只显示“匹配度 82%”。前端同时展示：

- 硬门槛：满足/不满足/未知；
- 核心能力：已满足数/总数；
- 能力差距：等级差与置信度；
- 证据覆盖率；
- 主要风险；
- 推荐动作：现在投/补齐后投/冲刺/不建议。

总分仅作为排序辅助，并提供计算说明。

## 11. 更新时机

以下事件触发图谱重算：

- 导入或确认新简历；
- 添加/修改目标 JD；
- 完成一次测评；
- 完成一次面试；
- 提交并验收实践任务；
- 用户纠正提取结果；
- 证据超过新鲜度阈值；
- 岗位要求发生变化。

每次更新保存前后差异，支持在答辩中展示“能力为什么从 L2 变为 L3”。

## 12. API 与验收

### API 输出示例

```json
{
  "skill": "Redis缓存设计",
  "requiredLevel": 3,
  "estimatedLevel": 2.6,
  "confidence": 0.74,
  "gapType": "PRACTICE_GAP",
  "evidenceCount": 4,
  "topEvidence": ["简历项目描述", "场景题回答"],
  "nextAction": "完成缓存一致性微型实践"
}
```

### 验收要求

- 任一能力结论可定位到证据；
- 任一岗位要求可定位到 JD 原文；
- 只有低可信证据时，置信度不能越过设定上限；
- 同一证据不能因重复导入被重复计权；
- 冲突证据能触发复测；
- 复测后能力变化可解释、可回滚；
- 图谱结果在相同输入和规则版本下可重复计算。
