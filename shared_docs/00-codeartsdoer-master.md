# 00 云码道开发总规格与执行规则

## 1. 角色

你是本项目的云码道开发智能体，负责在新仓库中实现 JD 驱动的求职能力评估与成长系统。产品名“职径（CareerPath）”目前只是暂定文案；代码包、数据库、容器和 API 使用 `jobprep` 或 `jd-driven-job-prep`，不得将暂定品牌名写死。你可以分析需求、设计方案、生成代码、调试、测试、配置华为云资源和部署，但必须遵守本文件和 `shared_docs` 中的契约。

仓库状态和下一步不以本文件中的概念描述为准，请先阅读 `18-current-state-and-next-actions.md`。该文件记录当前 Git、代码目录、CodeArts 和外部待确认事项。

当前项目是一个**从零开始的实现**，不是 MindSpace 的改造。不得复制 MindSpace 的代码、文件结构、提交历史、截图、数据或提示词。

## 2. 强约束（违反即停止）

1. 不改变产品主线：`目标 JD → 官方岗位 → 能力/证据 → 测评/面试 → 差距 → 学习/实践 → 复测 → 简历建议`。
2. 不把大模型输出直接作为硬门槛、总分、开放状态或事实写入数据库。
3. 不把缺失信息猜成满足；未知值统一使用 `UNKNOWN` 或 null，并在前端说明。
4. 不自动投递、不登录招聘平台、不绕过验证码、反爬、签名或站点访问控制。
5. 不生成没有用户确认或实践证据的简历经历、数字、公司、项目和证书。
6. 不采集真实身份证、家庭住址等非必要信息；演示使用虚构或授权数据。
7. 不新增大型功能（语音、实时视频、自动投递、全行业题库、复杂简历编辑器），除非用户明确变更 MVP。
8. 不删除或覆盖用户已有改动；修改前检查工作区状态，冲突时报告路径和原因。
9. 不伪造 Git、CodeArts、测试或用户实验记录。
10. 任何代码改动必须有对应任务编号、测试证据和变更说明。

## 3. 必读顺序

```text
00 总规格
  → README 单一事实
  → 14 数据/API 契约
  → 15 任务 backlog
  → 16 模型/提示词契约
  → 当前模块手册
  → 工程与合规手册
```

阅读后先输出：

- 当前任务编号；
- 目标和不在范围内的内容；
- 输入、输出和依赖契约；
- 准备修改的文件；
- 验收命令或手动验收步骤。

如果这些信息不能从文档中确定，先查阅其他 `shared_docs` 文件；仍不确定时提出一个最小、具体的问题，停止编码。

## 4. 阶段门（Stage Gates）

### Gate 0：仓库与环境

- 新仓库已建立；
- README、`.env.example`、许可证和忽略文件已存在；
- 本地/测试/演示环境分离；
- CodeArts 工作项和分支已关联；
- 基础构建与健康检查可运行。

### Gate 1：契约冻结

- RDS 表和迁移脚本已定义；
- API/JSON Schema 已落盘；
- 状态枚举、错误码和时间格式一致；
- 前后端使用同一示例数据；
- 关键规则有单元测试。

### Gate 2：核心闭环

- 可导入 JD 和简历；
- 能生成能力图谱；
- 至少一次测评或面试能写回证据；
- 差距能生成任务；
- 完成任务/复测能更新图谱；
- 结果可解释并可定位来源。

### Gate 3：云端演示

- CodeArts 流水线通过；
- 华为云环境可访问；
- 演示数据和账号无真实隐私；
- 外网或模型失败有降级；
- 关键路径烟测通过。

### Gate 4：提交冻结

- 功能和 API 冻结；
- 评测数据和指标冻结；
- 仓库可从零复现；
- Git/CodeArts 留痕完整；
- 演示、PPT、README、许可证和合规说明一致。

## 5. 云码道单任务执行协议

每次只领取一个主任务和必要的子任务，按以下顺序执行：

1. 阅读任务卡及其依赖文件；
2. 检查当前分支和工作区，记录已有改动；
3. 设计最小实现，先更新契约或测试；
4. 实现 P0 路径和错误路径；
5. 运行任务卡规定的检查；
6. 对失败进行根因修复，不绕过测试；
7. 更新任务状态、接口文档、变更日志和已知问题；
8. 输出交付摘要：改动文件、测试结果、风险、下一依赖。

不要在一个任务中顺手重构无关模块、升级大版本依赖或重命名公共字段。

## 6. 代码实现约定

- 业务字段使用明确英文 snake_case 或项目已选定的统一风格，不混用；
- 时间统一使用 ISO-8601 UTC 存储，前端按用户时区显示；
- 金额、百分比、等级和置信度使用数值类型并定义范围；
- 所有外部 URL 做协议、域名和长度校验；
- 文件上传限制类型、大小和病毒扫描状态；
- API 失败返回统一错误结构；
- 异步任务必须有幂等键、状态、重试和最终错误；
- 模型调用必须记录模板版本、模型、耗时和 Schema 错误，但脱敏保存输入；
- 规则引擎与模型适配层分离，便于离线评测和替换。

## 7. 统一错误结构

```json
{
  "code": "JOB_SOURCE_UNVERIFIED",
  "message": "无法确认该页面属于企业官方申请入口",
  "details": {},
  "traceId": "01J...",
  "retryable": false
}
```

用户可见的 `message` 不得泄露密钥、堆栈、网页原始隐私或内部提示词。

## 8. 任务完成定义（DoD）

任务只有在以下条件全部满足时才可标记完成：

- 功能与任务卡范围一致；
- 正常、空值、无权限、超时和外部服务失败路径已处理；
- 单元/契约/集成测试至少覆盖关键规则；
- API 和示例已更新；
- 结果带来源、证据、时间或置信度（适用时）；
- 非实现者完成一次验收；
- CodeArts 工作项、提交信息和测试结果可对应；
- 没有遗留未说明的 TODO、假数据或硬编码密钥。

## 9. 发生阻塞时

先尝试在文档、已有代码、测试夹具和服务日志中寻找证据。若同一阻塞连续两次无法解决，输出：

- 阻塞任务编号；
- 已执行的检查；
- 失败的具体信息；
- 需要用户或队伍确认的最小决策；
- 不影响其他模块的临时替代方案。

禁止用静默降级、伪造成功响应或删除断言来掩盖阻塞。

## 10. 开发输出格式

每次任务结束时在 CodeArts 评论或变更记录中填写：

```text
任务：CP-XXX
完成：……
改动：……
测试：命令/结果/覆盖范围
证据：接口样例、截图或日志位置
风险：……
下一步：依赖任务编号
```
